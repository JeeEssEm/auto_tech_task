# Задача: Оркестрация полного пайплайна и инвариантов через Taskiq

## Контекст
У нас уже есть спроектированный `ITZPipelineAdapter` (и его мок `MockITZPipelineAdapter`), а также базовый механизм сохранения статусов и отправки WebSocket-уведомлений на фронтенд. 

Теперь нам необходимо реализовать **конкретные цепочки фоновых задач (Taskiq)**, которые будут обслуживать реальные пользовательские сценарии (инварианты). Мы используем DI-контейнер `Dishka` (`FromDishka`) для внедрения зависимостей.

## Требования к реализации

Выступи в роли Senior Backend Python Developer. Напиши чисто, с обработкой ошибок и строгой типизацией набор Taskiq-задач (`broker.task`) для описанных ниже сценариев.

Во всех задачах **обязательно**:
1. Загружать текущий стейт `ITZPipelineAdapter` из БД (если это не первичная генерация).
2. Подключать `notifier` (функцию, которая пишет статус в БД и кидает ивент в Redis).
3. После завершения LLM-операций — сохранять новый стейт адаптера (`adapter.save_state()`) обратно в БД.
4. В случае `Exception` отлавливать ошибку, сохранять статус `ERROR` в БД и уведомлять фронтенд.

## Сценарии (Инварианты), которые нужно покрыть:

### 1. Полный пайплайн первичной генерации (Создание чата)
**Флоу:**
- Пользователь создал чат и загрузил файлы.
- *Шаг 1 (уже есть, мокаем):* Парсинг файлов (извлечение текста).
- *Шаг 2:* Инициализация пустого `ITZPipelineAdapter`.
- *Шаг 3:* Запуск аналитики — вызов `await adapter.ingest_sources(parsed_files)`.
- *Шаг 4:* Сборка итогового ТЗ — вызов `await adapter.compile_document()`.
- *Шаг 5:* Сохранение итогового ТЗ (результата) в БД/S3 и стейта пайплайна.

### 2. Обновление ТЗ (Новые данные + Комментарий)
**Флоу:**
- Пользователь уже имеет сгенерированное ТЗ, но загрузил еще 1 файл (например, pdf) и/или написал глобальный комментарий (например, "Учти этот файл и сделай ТЗ более строгим").
- *Шаг 1:* Загрузка стейта адаптера из БД.
- *Шаг 2:* Парсинг нового файла (мокаем результат парсинга).
- *Шаг 3:* Если есть новые файлы -> `await adapter.ingest_sources(new_files)`.
- *Шаг 4:* Если есть текст комментария -> `await adapter.apply_global_comment(comment)`.
- *Шаг 5:* Пересборка ТЗ (`compile_document` или возврат обновленного результата из `apply_global_comment`).
- *Шаг 6:* Сохранение нового стейта и нового ТЗ в БД.

### 3. Точечная перегенерация блока ТЗ
**Флоу:**
- Пользователь нажал "Перегенерировать" возле конкретного блока ТЗ.
- *Шаг 1:* Загрузка стейта из БД.
- *Шаг 2:* Вызов `await adapter.regenerate_block(field_path, instruction)` (инструкция может быть пустой, если юзер просто нажал рефреш, или содержать пожелание "сделай покороче").
- *Шаг 3:* Сохранение измененного стейта и обновленного ТЗ.

### 4. Генерация/Заполнение кастомного или пустого блока
**Флоу:**
- Пользователь добавил блок руками через UI (например, "Требования к анимациям") и нажал "Заполнить с помощью AI", ИЛИ нажал "Заполнить" у существующего обязательного пустого блока.
- *Шаг 1:* Загрузка стейта из БД.
- *Шаг 2:* Вызов `await adapter.generate_custom_block_content(field_path, custom_topic)`.
- *Шаг 3:* Сохранение стейта и ТЗ.

## Ожидаемый результат

Создай файл `backend/worker/tasks/tz_pipeline_tasks.py`.

В этом файле:
1. Опиши вспомогательную фабрику/функцию `get_notifier_callback(chat_id, redis, db)`, чтобы не дублировать код уведомлений в каждой таске.
2. Реализуй 4 Taskiq-задачи (`@broker.task`) под описанные выше инварианты.
3. Покажи, как грамотно передавать данные между тасками (например, если парсинг — это отдельная таска, как она вызывает таску генерации ТЗ, или как они объединяются в пайплайн через Taskiq Taskiq dependencies/chaining).

Используй `Dishka` для инъекции зависимостей (например, `chat_repo: FromDishka[ChatRepository]`, `pipeline_repo: FromDishka[PipelineRepository]`, `redis_client`).

Убедись, что архитектура позволяет легко заменить `MockITZPipelineAdapter` на боевой класс без изменения самих Taskiq-задач.
